Cross-plan interaction scenarios

The scenarios that actually broke this session all involved two different plans interacting — a gate that's correct in isolation can still misbehave once both sides of an interest are real accounts. Each plan's own checklist above assumes you're the only variable; these assume you aren't.

TC-1

Mismatched chat access — one side below Silver

  1. VannClassic (700) sends interest to VannStarter (699, opposite gender pair needed — substitute accordingly)
  2. Starter side accepts
  3. Classic side opens chat — Classic's MESSAGE is unlimited, should work
  4. Starter side opens the same conversation
Classic viewerChat opens, can send
Starter viewerCounts as 1 of Starter's 5 allowed distinct conversations — this specific chat stays open regardless of message count; the cap only blocks starting a 6th different conversation
TC-2

Both sides below Silver — the "matched but mute" case

  1. VannFree (696) sends to VannStarter (699)
  2. Starter accepts
  3. Both sides check Matches count, then try to open chat
Matches countIncrements for both — Matches is symmetric, unrelated to chat access

Starter side chatOpens (has 5 messages), but talking to a Free account that can never reply is a dead end worth flagging as a product question, not a bug
TC-3

Classic reveal quota is per-viewer, not per-conversation

  1. VannClassic (700) reveals contact for VannSilver (703) — uses 1 of 40
  2. VannClassic (700) reveals contact for VannGold (705) — uses 1 of 40 (total: 2 used)
  3. VannClassic (700) re-opens VannSilver (703)'s profile
Quota after step 238 of 40 remaining, shared across every profile — not 40 per profile

TC-4

Re-send after decline vs. re-send after cancel

  1. VannClassic (700) sends to VannSilver (703)
  2. Path A: Silver declines → Classic re-sends from the profile screen
  3. Path B: instead, Classic cancels their own request from "Sent By You" → re-sends
Path A resultRe-send succeeds, resets the same row to PENDING — fixed 2026-07-08
Path B resultRe-send succeeds without a 500 error (conversations duplicate-key) — fixed 2026-07-09, this is the one most worth regression-testing since it was a server crash, not just a bad message
TC-5

Send-quota consumption is independent of outcome

  1. VannFree (696) sends all 3 lifetime interests to three different accounts
  2. Leave one PENDING, get one REJECTED, cancel one yourself
Requests remaining0, regardless of the three different outcomes above — quota is consumed at send time and never refunded for any reason

Recheck: bugs fixed this session

Everything below was an actual reported failure, fixed in the 2026-07-08/09 sessions. Confirm each one before considering plan-gating "signed off" — several touch the same files as the checklists above.

  • Interest send silently "succeeded" on a duplicate. handleSendInterest now checks res.data.code === 201 before showing success — resend to an account with a PENDING/APPROVED row already should show a real error, not a false "sent."
  • Re-send after decline was blocked forever. Now resets the same row to PENDING. Test via TC-4 Path A above.
  • conversations duplicate-key 500 on re-send after cancel. The highest-severity fix this session — a real server crash. Test via TC-4 Path B.
  • Request quota frozen at plan default, never decrementing. Caused by missing user_subscriptions rows on bulk-seeded accounts; backend now self-heals via ensureActiveSubscription. Confirm on any account, not just the Vann* set, since real users could theoretically hit this too if a signup ever fails partway.
  • "Interests & Hobbies" edit was a raw text input that silently failed to save. Now a proper multi-select chip grid via EditInterestsModal.tsx, used by both the Profile screen and the profile-edit tabs.
  • Android: could not tap anything except the Quick Access FAB. Root cause was a second GestureHandlerRootView. Test specifically on Android, not iOS — this never reproduced there.
  • Footer nav stuck on "Home" after editing profile data. VVMFooterNav now syncs its highlighted tab to the real navigation state instead of only seeding once.
  • Last item in Received/Sent/Permissions lists hidden behind the floating footer. Check with 4+ items in each of the three mailBox tabs.
  • Classic Reveal Contact button + accurate horoscope-empty message. The two fixes this exact conversation was about — see the Classic section above and TC-3.

Frontend / DB drift — worth a product decision, not just a test

These aren't bugs so much as places where the DB says one thing and the code enforces something looser or nothing at all. Testing them means confirming the current behavior is intentional, or filing them as real gaps.

Critical — found 2026-07-10 PremiumTab.tsx (the actual "Upgrade" screen every real user sees) does not call any backend endpoint for plan data. It renders entirely from a hardcoded MOCK_API_RESPONSE object (and an identical defaultPlans error-fallback) — both completely disconnected from the real subscription_plans/planFeatures tables. Examples of what users are currently shown vs. reality: Starter listed at ₹199 (real: ₹499) with copy saying "15 interests" (real Starter quota: 25); Classic listed at ₹999/₹1,499 across two duplicate duration variants (real: single ₹999/90-day plan) with copy saying "50 interest requests" (real Classic quota: 15, now 60 locally). None of the six real plans, prices, or durations match what's on screen. This predates and is unrelated to today's SEND_REQUEST fix, but it means the marketing copy was already wrong before the fix and is still wrong after it — fixing the DB number alone does not fix what customers actually read. A real fix requires either wiring this screen to userApi.getAllActivePlans() (which already exists at /subscriptionPlans/getAllActivePlans and is unused) or rewriting the mock data to match the real 6-plan structure. Not yet decided or scheduled — flagging for a product call.
